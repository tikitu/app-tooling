# app-tooling

> **Made with an AI coding agent.** This repository was written largely by an
> LLM coding agent (Claude, in Claude Code), working under my direction and
> review, as were the apps it was distilled from. I say so up front so that
> anyone who would rather not use work made this way can decide that for
> themselves.

The technical setup I use to build Mac (and iOS) apps with agents, gathered
in one place.

There are three ways in:

- **An agent in a new project**, which starts from the starter.
- **An agent in an existing project**, bringing it into line with a
  pattern, or up to date with one it already has.
- **A human**, who wants to know what each part is, what it does for you,
  and above all *why* I prefer it.

It is about the *technical* capabilities: building, running, checking and
linting an app. How a project is run (where plans live, commit and merge
rules) differs between teams, so it is offered as opt-in practices rather
than built in.

## Starting a new Mac app

```sh
cp -R starter ~/code/MyApp && cd ~/code/MyApp && git init
scripts/new-app.sh --list                     # the practices on offer
scripts/new-app.sh MyApp --with <practices>   # a list, `all` or `none`
```

An agent setting up a project should show the user the `--list` and ask
which practices they want. [`starter/README.md`](starter/README.md) has the
rest of the first steps; [`starter/practices/README.md`](starter/practices/README.md)
explains each practice and why you might want it.

Pieces that live elsewhere (skills, command-line tools) and how to get them
are in [external.md](external.md).

## Bringing an existing app into line

[`patterns/`](patterns/README.md) holds conventions packaged for apps that
already exist: each says how to recognise what a project has already, what
to change, and how to check it worked. Projects import them with
[peru](https://github.com/buildinspace/peru), pinned at one commit of this
repository, following a release tag or a branch; `make app-tooling-update`
brings a project up to date and prints the steps it needs. Start with
[`patterns/pattern-imports`](patterns/pattern-imports/README.md).
Releases: [`RELEASING.md`](RELEASING.md), [`CHANGELOG.md`](CHANGELOG.md).

Improvements found in other projects start in [`inbox/`](inbox/README.md).

## What the starter brings

Always, as the core:

- **Build.** SwiftPM only, no Xcode project: `make` and `build.sh` build,
  bundle and ad-hoc sign the `.app`; `make dist` signs, notarizes, staples
  and zips a release. The app icon is drawn by a Swift script.
- **Platforms split by package, not by `#if`.** A shared package that
  declares macOS and iOS and is compiled for iOS by `make check`, so Mac-only
  API cannot creep in before there is an iOS app; a Mac-only package for the
  app. A lint rule forbids `#if os(…)`.
- **Pinned dependencies.** Each package's `Package.resolved` is committed and
  every build uses it; every build also checks the two packages pin the same
  versions (`make check-pins`). `make outdated` and `make update-pins` make
  updates a reviewable diff.
- **Architecture.** The Point-Free libraries, one `AppModel`, and every
  control performing an `AppCommand` through it, so a script reaches
  everything a click does. Nonisolated default actor isolation.
- **Verifying without a human, and without taking focus.** A command inbox
  on scratch data (`make run-scratch`, `scripts/send-commands.sh`), keys
  posted to the process (`send-keys.swift`), screenshots by window id
  (`make screenshot`). `make run` opens in front for a person;
  `make run-background` is the agent's.
- **Keyboard-driven lists on the Mac.** Explicit selection on the model, →
  for an actions menu, and the selection moving on after acting.
- **Lint rules that carry their own reasoning.** ast-grep rules for mistakes
  that fail silently or keep coming back, each beside a document saying why
  it exists and what to do when it fires, and each with a test that shows it
  firing. `AGENTS.md` tells agents to read the document before working
  around a rule, and to turn recurring mistakes into new rules. Plus
  `swift format` with one canonical form.
- **Every build knows its commit.** `AppGitCommit` in the bundle's
  `Info.plist` (the `git-commit-stamp` pattern).
- **Patterns, from the start.** A `peru.yaml` importing the patterns the
  starter carries, so a new app is updated like any other.
- **`docs/gotchas.md`.** Traps that looked like something else, and why the
  odd-looking code that avoids them is there.
- **Patterns for when the app grows.** `docs/screens.md`: a second screen
  declared once as data, a window on the Mac and a sheet on iOS.
  `docs/ios.md`: an iOS app in its own package, with an Xcode project
  generated by XcodeGen and git-ignored.
- **`AGENTS.md`.** The instructions for all of the above. Claude Code reads
  `AGENTS.md` when there is no `CLAUDE.md` (since 2.1.277), so it is the only
  instruction file.

Optional extras which can be chosen at project-creation time: markdown project
tracking (`PLAN.md`/`PROGRESS.md`/`PROBLEMS.md`), docs in step with behaviour,
commit-to-main, commit hygiene, no self-merge, and (for projects with
snapshot tests) reviewing re-recorded snapshots before committing them.

## Also here

- **[`SWIFTUI-RULES.md`](SWIFTUI-RULES.md).** SwiftUI-on-the-Mac rules, each
  with the failure that taught it: transition crashes, layout, stale caches,
  rows, toolbars, Charts. Complements the `swiftui-pro` skill.
- **[`skills/derived-data-cleanup`](skills/derived-data-cleanup/SKILL.md).**
  A Claude Code skill that finds Xcode DerivedData directories whose
  project or worktree is gone, proven from the path each one records, and
  deletes only those. Not a pattern: install it once, for every project,
  with `ln -s ~/code/app-tooling/skills/derived-data-cleanup
  ~/.claude/skills/derived-data-cleanup`.
